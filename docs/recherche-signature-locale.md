# Signature locale — prémisse optionnelle pour le lot 7

Recherche du 17 octobre 2026, sources officielles uniquement. **Faits** documentaires, **proposition** d’adaptateur et **preuves manquantes** restent séparés. Aucun prestataire choisi par le cabinet ; cette note ne vaut ni activation, ni contrat souscrit, ni garantie juridique. Le [contrat canonique et les simulations](recherche-documents-locaux.md#gel-aperçu-et-signature--règles-proposées) ne prouvent aucun protocole fournisseur exploité.

## Faits : deux possibilités auto-hébergées

**DocuSeal communautaire** : API et webhooks, SMTP, stockage disque, SQLite par défaut ou PostgreSQL/MySQL ; licence AGPLv3 avec conservation de l’attribution dans l’interface. Les imports de modèles PDF/DOCX/HTML par API et l’intégration embarquée figurent dans les fonctions Pro ([README et licences](https://github.com/docusealco/docuseal/tree/3c65b0e4ba872fe71d5566c0d09c3ace59a7fb8a)). L’API permet `POST /submissions` depuis un `template_id` existant, destinataires par rôle/email, ordre conservé/parallèle et `send_email:false` ; `POST /submissions/pdf` est explicitement Pro. `GET /submissions/{id}` expose notamment statut/audit ; `/documents` renvoie aussi des documents partiels avant achèvement ([API officielle](https://www.docuseal.com/docs/api)). Donc le gratuit convient à des modèles préalablement préparés, mais n’établit pas l’import automatisé du PDF propre à chaque lettre générée par Memlia.

Au commit cité, DocuSeal signe réellement `X-Docuseal-Signature = timestamp.HMAC-SHA256(secret, timestamp.rawBody)` ; tolérance documentée/source de cinq minutes. Des en-têtes secrets personnalisés existent également. Ce mécanisme est vérifié dans le [signataire](https://github.com/docusealco/docuseal/blob/3c65b0e4ba872fe71d5566c0d09c3ace59a7fb8a/lib/webhook_urls/signatures.rb) et [l’émetteur](https://github.com/docusealco/docuseal/blob/3c65b0e4ba872fe71d5566c0d09c3ace59a7fb8a/lib/send_webhook_request.rb), sans extrapolation à une ancienne version. Le présent adaptateur proposé ci-dessous concerne **Documenso**, dont l’authentification diffère.

**Documenso communautaire** documente création PDF, rôles signataire/approbateur, ordre, REST et webhooks sans licence Enterprise ; socle AGPL-3.0, fonctionnalités Enterprise sous licence distincte. Le mainteneur précise que la présence du paquet `ee` n’impose pas de le retirer pour exploiter le communautaire sans activer ses fonctions Enterprise ([capacités](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/policies/community-edition.mdx), [clarification officielle](https://github.com/documenso/documenso/issues/3110)). La [release v2.20.0](https://github.com/documenso/documenso/releases/tag/v2.20.0), publiée le 8 octobre 2026, contient les routes examinées. L’API v2 peut évoluer : figer release, image/digest et schéma ; employer `/envelope/*`, les anciennes créations document/template étant dépréciées ([versionnement](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/developers/api/versioning.mdx)).

## Faits : contrat Documenso v2.20.0 exploitable

Base auto-hébergée `<instance>/api/v2`, en-tête `Authorization: api_…` ([authentification](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/developers/api/index.mdx)).

| Opération | Contrat constaté |
| --- | --- |
| Préparer | `POST /envelope/create`, multipart `payload` JSON + `files` PDF. `type:DOCUMENT`, `title`, `externalId`, `recipients` ; champs `SIGNATURE` avec `identifier:0`, page dès 1, positions/dimensions en pourcentage. Retour `{id}` ; état initial `DRAFT` ([schéma](https://github.com/documenso/documenso/blob/v2.20.0/packages/trpc/server/envelope-router/create-envelope.types.ts), [modèle](https://github.com/documenso/documenso/blob/v2.20.0/packages/prisma/schema.prisma)). |
| Destinataires/approbation | `email`, `name`, `role`, `signingOrder` ; `SIGNER`, `APPROVER`, `CC`, `VIEWER`. Configurer explicitement `meta.signingOrder:SEQUENTIAL` pour un approbateur préalable ; l’approbation humaine Memlia demeure distincte ([rôles et ordre](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/developers/api/documents.mdx)). |
| Envoyer/suivre | Après validation seulement, `POST /envelope/distribute` avec `envelopeId` ; retour identifiant et liens de signature. `GET /envelope/{envelopeId}` retourne état/destinataires/items. États documentés : `DRAFT`, `PENDING`, `COMPLETED`, `REJECTED`, `CANCELLED` ([distribution](https://github.com/documenso/documenso/blob/v2.20.0/packages/trpc/server/envelope-router/distribute-envelope.types.ts), [lecture](https://github.com/documenso/documenso/blob/v2.20.0/packages/trpc/server/envelope-router/get-envelope.types.ts)). |
| Récupérer | GET `/envelope/item/{envelopeItemId}/download?version=signed`, `/envelope/{envelopeId}/audit-log/download`, `/envelope/{envelopeId}/certificate/download` : PDF authentifiés. `signed` sert les octets courants sans vérifier l’achèvement ; exiger côté Memlia `status:COMPLETED`. Le rapport certificat accepte aussi `REJECTED` via son prédicat interne, donc sa présence seule ne prouve pas la signature complète ([implémentation HTTP effective](https://github.com/documenso/documenso/blob/v2.20.0/apps/remix/server/api/download/download.ts), [service des octets](https://github.com/documenso/documenso/blob/v2.20.0/apps/remix/server/api/files/files.helpers.ts), [prédicat](https://github.com/documenso/documenso/blob/v2.20.0/packages/lib/utils/document.ts)). |

Les webhooks sont configurés pour une **équipe**. Événements : création, envoi, ouverture, signature individuelle, action d’un destinataire, achèvement global, rejet, annulation et expiration d’un destinataire. Un événement individuel ne prouve pas l’achèvement ; l’expiration d’un lien ne constitue pas un état global inventé ([événements](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/developers/webhooks/events.mdx)).

**Authentification exacte :** secret statique dans `X-Documenso-Secret`, comparaison constante ; aucun HMAC ni horodatage cryptographiquement signé. Imposer un secret non vide et TLS hors fixture. L’émetteur envoie `{event,payload,createdAt,webhookEndpoint}` ; `createdAt` est recréé à chaque tentative, sans identifiant stable d’événement exposé. Corréler `payload.envelopeId` et `externalId`, pas son ancien `id` numérique ([transport](https://github.com/documenso/documenso/blob/v2.20.0/packages/lib/server-only/webhooks/execute-webhook-call.ts), [tentative](https://github.com/documenso/documenso/blob/v2.20.0/packages/lib/jobs/definitions/internal/execute-webhook.handler.ts), [payload](https://github.com/documenso/documenso/blob/v2.20.0/packages/lib/types/webhook-payload.ts)).

## Proposition : plus petit adaptateur optionnel

Construire uniquement `documenso-v2.20`, désactivé par défaut : URL locale explicitement autorisée, références de secrets locales, équipe, préparation/envoi séparés, lecture et téléchargement. Conserver version GED, PDF téléversé, empreinte, destinataires/positions, identifiants fournisseur et artefacts récupérés. L’import normalise/aplatit le PDF et retire les placeholders : relire le PDF fournisseur `original`, conserver son empreinte et refaire approuver l’aperçu transformé avant distribution ; ne pas promettre des octets identiques ([création réelle](https://github.com/documenso/documenso/blob/v2.20.0/packages/trpc/server/envelope-router/create-envelope.ts)).

Aucune garantie `Idempotency-Key` n’est établie par les schémas consultés ; `externalId` n’est pas unique dans le modèle cité. Prévoir journal/outbox et verrou locaux ; après timeout de création/envoi, réconcilier l’objet et ses destinataires, sinon état incertain avec intervention, jamais réémission aveugle. Réception durable puis accusé rapide ; dédupliquer transitions/artefacts indépendamment de `createdAt`, relire l’état authentifié avant finalisation, empêcher régression et rejouage produisant un effet métier supplémentaire. Un secret statique seul n’empêche pas le replay.

Fixture HTTP locale à réaliser : multipart/auth exacts, approbation périmée, 401/429/5xx/timeout, réponse perdue, corrélation inconnue, événements doublés/désordonnés, rejet/expiration partielle, PDF tronqué/HTML/absent et preuve manquante. Vérifier aucune distribution avant validation ; `COMPLETED` fournisseur avec téléchargement échoué reste « preuve à récupérer ».

## Installation et preuves manquantes

Documenso nécessite PostgreSQL, secrets de chiffrement/session, stockage local en base ou stockage S3 auto-hébergé, certificat `.p12` fourni par l’exploitant et expéditeur/SMTP autorisé. La file locale utilise PostgreSQL. Isoler service/base/clé/certificat, sauvegarder/restaurer, borner les sorties ; une route distante sécurisée reste nécessaire aux signataires extérieurs ([installation](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/self-hosting/deployment/docker-compose.mdx), [stockage](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/self-hosting/configuration/storage.mdx), [courriel](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/self-hosting/configuration/email.mdx)). Les callbacks privés demandent une autorisation ciblée `NEXT_PRIVATE_WEBHOOK_SSRF_BYPASS_HOSTS` ; aucun tunnel cloud nécessaire. Délai webhook 10 s ; reprises dépendantes de la file, pas de livraison garantie ([configuration](https://github.com/documenso/documenso/blob/v2.20.0/apps/docs/content/docs/developers/webhooks/setup.mdx)).

**Absent :** installation, fixture exécutée, rendu fournisseur, signature, réception email, restauration et validation cabinet. Ni certificat auto-signé ni rapport PDF ne garantissent un niveau juridique. Aucun compte, abonnement, conteneur, courriel, requête de signature ou changement de dépendances/configuration réalisé. Si le cabinet choisit ailleurs, adapter au contrat réellement obtenu ; contrat absent = simulation visible et envoi réel désactivé. La [recette finale](validation-connecteurs.md#5-accès-complémentaires-du-périmètre-fonctionnel) et les exclusions restent inchangées.

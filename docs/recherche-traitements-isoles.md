# Traitements de fichiers isolés — décision préparatoire

Recherche du 17 octobre 2026, sources primaires. **Fait** = source/documentation consultée ; **proposition** = travail à construire ; **preuve absente** = aucune garantie opérationnelle acquise. Complète les recherches [imports](recherche-imports-referentiel.md) et [documents](recherche-documents-locaux.md), sans reprendre leurs choix de parseurs.

## Écart constaté

**Fait local :** [Dockerfile](../Dockerfile) fige Node **22.22.3**, Debian Bookworm, sans LibreOffice installé. [Compose](../deploy/compose.yaml) retire les capacités et impose `no-new-privileges` à l’application ; celle-ci conserve réseau, secrets et accès inscriptible à toute `/data`. Aucun worker dédié, plafond mémoire/CPU/PID ou racine en lecture seule n’y est déclaré. Ce conteneur applicatif ne constitue donc pas le périmètre réduit recherché pour un fichier hostile.

**Fait local :** [l’extraction PDF](../apps/server/src/documents/content.ts) lance un enfant avec `--max-old-space-size=128`, délai 30 s et `maxBuffer` 25 Mio. Le [worker](../apps/server/src/documents/pdf-worker.mjs) limite pages/texte et utilise des assets locaux. **Limite :** V8 borne sa vieille génération, pas toute la mémoire du processus ; buffers, code natif et descendants ne sont pas un plafond RSS. Le délai Node envoie un signal, `killed` ne prouve pas la terminaison et tuer le parent ne tue pas nécessairement les petits-enfants ([CLI 22.22.3](https://nodejs.org/download/release/v22.22.3/docs/api/cli.html#--max-old-space-sizesize-in-mib), [child_process 22.22.3](https://nodejs.org/download/release/v22.22.3/docs/api/child_process.html#subprocesskillsignal)).

**Fait versionné :** dans Node 22.22.3, `--permission` est stable depuis 22.13.0 ; restrictions sur fichiers, enfants, threads, addons, WASI et inspecteur. **Aucune permission réseau n’est exposée dans cette version.** La documentation exclut explicitement toute garantie contre du code malveillant : le modèle protège des erreurs de code de confiance. Des descripteurs existants contournent le contrôle et des liens symboliques peuvent sortir des chemins accordés ; les threads n’héritent pas du modèle ([permissions 22.22.3](https://nodejs.org/download/release/v22.22.3/docs/api/permissions.html)). **Proposition :** couche supplémentaire facultative pour un lecteur Node compatible ; jamais justification du confinement, ni politique transmissible à LibreOffice.

## Mécanismes supportés et limites

| Besoin | Fait documenté | Conséquence proposée |
| --- | --- | --- |
| Mémoire et débit CPU | Docker applique `--memory` et `--cpus` ; mémoire + swap de même valeur interdit le swap si supporté. Par défaut ces ressources ne sont pas bornées ([ressources](https://docs.docker.com/engine/containers/resource_constraints/)). | Limiter le **conteneur du travail entier**, descendants compris ; `--cpus` limite un débit, pas un temps total. Vérifier le support effectif du noyau. |
| Réseau extérieur | `--network none` crée uniquement loopback ([pilote none](https://docs.docker.com/engine/network/drivers/none/)). | Aucun réseau partagé avec app/base, aucun socket réseau ou Unix hérité/monté ; loopback reste disponible dans le travail. |
| Écritures persistantes | `--read-only` rend la racine en lecture seule ; les montages inscriptibles restent des exceptions ([référence run](https://docs.docker.com/reference/cli/docker/container/run/)). | Entrée unique en lecture seule, aucun montage GED/base/config/secrets/domicile, travail temporaire explicitement autorisé. |
| Espace temporaire | `tmpfs` accepte taille, UID/GID, mode, `noexec,nosuid,nodev` ; sa mémoire compte dans la limite cgroup. Il peut utiliser le swap ([tmpfs](https://docs.docker.com/engine/storage/tmpfs/)). | Dimensionner scratch **dans** le budget mémoire, limiter aussi les inodes ; pas de sortie hôte sans quota par simple bind mount. |
| Processus et privilèges | Docker expose `--pids-limit`, utilisateur non root, retrait de capacités, `no-new-privileges`, espace PID privé ([run](https://docs.docker.com/reference/cli/docker/container/run/)). Seccomp par défaut filtre des appels système ([profil officiel](https://docs.docker.com/engine/security/seccomp/)). | Conserver ces protections ; ne pas employer `privileged`, namespaces hôte, devices ou profil `unconfined`. |

**Fait :** les cgroups Linux sont hiérarchiques et les enfants naissent dans celui du parent ; ils organisent/limitent les ressources, sans être à eux seuls un contrôle fichiers/réseau ([noyau cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)). Docker conserve un noyau partagé : la documentation reconnaît les risques d’isolation incomplète et de vulnérabilités noyau ([sécurité Engine](https://docs.docker.com/engine/security/)). Ces mécanismes donnent un périmètre OS concret, pas une preuve d’invulnérabilité.

## Petite option proposée : un conteneur neuf par travail

**Proposition privilégiée pour Linux cabinet :** un lanceur local de confiance crée un conteneur éphémère à commande/image fixes : lecteur imports pour Task 1, PDF pour GED, convertisseur LibreOffice pour Task 7. Un protocole court transporte identifiant, octets bornés et résultat ; aucun paramètre Docker, image, commande ou chemin hôte arbitraire venant du client. Le lanceur reste **hors** du conteneur applicatif. Le socket Docker donne des pouvoirs étendus sur l’hôte et ne doit pas être monté dans l’app/worker ([surface du daemon](https://docs.docker.com/engine/security/#docker-daemon-attack-surface)). Ce lanceur est une nouvelle pièce d’exploitation à spécifier/tester, pas une capacité actuelle.

**Proposition de configuration initiale, non mesurée :** `--network=none --read-only --user=<uid>:<gid> --cap-drop=ALL --security-opt=no-new-privileges=true --pids-limit=64 --cpus=1 --init`, espace PID privé ; entrée régulière unique en lecture seule ; un scratch tmpfs borné, HOME/TMPDIR/cache/profil dedans. Racine construite sans données cabinet. Vérifier également `/dev/shm` et les montages techniques : `--read-only` ne signifie pas littéralement qu’aucun octet ne peut s’écrire hors `/scratch`. Le critère est aucune écriture persistante hors scratch autorisé, aucune donnée cabinet accessible.

| Travail | Budget mémoire **avec scratch**, swap total égal | Scratch maximum | Échéance murale |
| --- | --- | --- | --- |
| CSV/XLSX | 256 Mio | 64 Mio | 10 s |
| PDF | 512 Mio | 128 Mio | 30 s |
| DOCX → LibreOffice | 768 Mio | 256 Mio | 60 s |

**Proposition :** un travail actif par installation initialement ; seuils à ajuster avec les quotas applicatifs déjà proposés. Les 768 Mio LibreOffice remplacent ici l’hypothèse antérieure de 512 Mio pour réserver du scratch, sans mesure justifiant encore l’un ou l’autre. Le CPU, la mémoire et les PID doivent couvrir aussi l’init et le lanceur interne. Précontrôles ZIP/XML eux-mêmes dans ce périmètre ; aucun parseur hostile avant isolation.

**Proposition :** contrôleur extérieur avec échéance depuis l’admission, arrêt du conteneur puis SIGKILL après 2 s ; vérifier arrêt/removal avant libérer le slot. `docker stop` prévoit TERM puis KILL ; tuer seulement le client Docker n’est pas arrêter le travail ([stop](https://docs.docker.com/reference/cli/docker/container/stop/), [kill](https://docs.docker.com/reference/cli/docker/container/kill/)). Quand le PID 1 d’un espace PID Linux meurt, le noyau tue les processus restants de cet espace ([manuel Linux](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)). Un blocage noyau/daemon peut dépasser l’échéance : publier une erreur, fermer l’admission et réconcilier les travaux abandonnés au redémarrage. Sortie et diagnostics bornés ; ne publier que résultat complet validé. Récupérer la sortie pendant la vie du conteneur si elle réside en tmpfs, puis supprimer celui-ci ; refuser liens et fichiers spéciaux.

**Fait LibreOffice :** profil inscriptible requis ; `-env:UserInstallation=file:///scratch/profile`, `--headless`, `--norestore`, `--convert-to` et `--outdir` sont documentés ([paramètres](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)). **Proposition :** profil neuf par conversion, réglages macros/contenus actifs déjà définis dans la recherche documents ; aucune réutilisation du bureau ou UNO ouvert. Headless/profil privé ne remplacent pas les frontières OS.

## Développement Mac et preuve attendue

**Proposition :** Mac utilise le même worker Linux dans Docker Desktop, qui exécute une VM Linux ([VMM officiel](https://docs.docker.com/desktop/features/vmm/)). Qualifier architecture, polices, permissions des montages et limites de cette VM. Un enfant Node/LibreOffice natif reste utile sur fixtures fictives ; il n’apporte pas la preuve des cgroups/namespaces Linux. Une sandbox Linux assemblée directement serait possible avec plusieurs mécanismes distincts, mais ajouterait un second chemin d’exploitation sans bénéfice démontré ici.

**Preuves absentes :** aucun conteneur lancé, aucune installation, aucun corpus hostile exécuté. À réaliser Task 1 puis Task 7/11 : tentatives contrôlées de lecture/écriture sentinelles, réseau IPv4/IPv6/DNS/Unix, saturation mémoire/native/buffers/scratch/PID/CPU, enfant ignorant TERM et petit-enfant, panne du contrôleur, reprises et absence de sorties partielles. Inspecter configuration réelle, événements OOM et consommation ; tester avec ressources cabinet réservées. Sans ces résultats sur Linux cible, le code actuel ne doit pas être déclaré protégé contre des fichiers hostiles. La recherche seule ne livre aucune de ces garanties.

## Alternative : service worker fixe

**Fait :** Compose expose `network_mode: none`, `read_only`, `cap_drop`, `security_opt`, `mem_limit`, `memswap_limit`, `cpus`, `pids_limit` et `tmpfs` ([services](https://docs.docker.com/reference/compose-file/services/)). Des conteneurs peuvent partager un volume indépendamment de leur réseau ([volumes](https://docs.docker.com/engine/storage/volumes/)) ; un tmpfs propre à un conteneur n’est pas partageable ([tmpfs](https://docs.docker.com/engine/storage/tmpfs/)). Un répertoire partagé peut porter un socket Unix, comme l’illustre le montage du socket Engine ([run](https://docs.docker.com/reference/cli/docker/container/run/#mount-volume-read-only---read-only)) : ici, il porterait uniquement le socket métier.

**Proposition :** un service fixe non root, sans montage app/base/secrets, assure successivement imports, PDF et DOCX ; commande/image fixes, réseau none, racine RO, capacités retirées et scratch borné. Partager seulement un répertoire de socket aux permissions contrôlées ; transférer les octets par protocole borné, scratch restant privé. Un spool partagé est possible mais ajoute chemins, liens, quotas disque et nettoyage ; un volume ordinaire ne fournit pas le plafond du tmpfs. L’app revalide schéma, taille, identité/empreinte et état complet du résultat avant publication.

**Compromis proposé :** évite lanceur hôte/API Docker, simplifie Compose ; limites mémoire/CPU/PID portent sur **tout le service**, superviseur compris, avec un seul travail actif. Ce service durable ne recrée pas la frontière entre travaux : contamination du processus/scratch ou compromission peut atteindre les suivants et son protocole. File bornée, admission, échéance, annulation, terminaison des descendants, nettoyage et reprise restent à construire ; un superviseur dans le même conteneur n’est pas une frontière indépendante contre sa compromission. Le conteneur éphémère fournit un renouvellement et un contrôle d’arrêt extérieurs plus nets.

**Proposition exploitation :** tout producteur sidecar rejoint le stop/drain de sauvegarde cohérente Task 5, actuellement centré sur l’app ; arrêter l’admission et figer/réconcilier les résultats avant sauvegarde. `stop_grace_period` règle TERM→KILL, sans implémenter ce protocole ([services](https://docs.docker.com/reference/compose-file/services/#stop_grace_period)). **Preuve absente :** aucun sidecar ni confinement/arrêt intertravaux testé ; alternative faisable à qualifier, pas protection déjà livrée.

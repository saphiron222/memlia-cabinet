## Images et paquet proposés

**Fait :** les images Node Bookworm reposent sur Debian 12/glibc ; Alpine utilise musl, dont la compatibilité diffère. **Proposition :** construire et exécuter sur la même famille Debian, Node ≥22.22.0, avec dépendances natives construites pour la cible Linux ([projet officiel Node Docker](https://github.com/nodejs/docker-node/blob/main/README.md#image-variants)).

**Fait interrogé :** le registre officiel Docker a répondu avec les index OCI suivants ; ce sont des images disponibles, pas des images exécutées ici ni une affirmation de dernière version. Chaque index contient notamment des manifestes Linux amd64 et arm64 distincts.

**Proposition :** figer tag + digest dans la livraison, enregistrer architecture et versions réellement exécutées ; qualifier d’abord Linux amd64. Un index multiarchitecture disponible ne prouve ni un build applicatif arm64 ni une restauration testée sur cette cible. Réinterroger les digests lors d’une mise à jour contrôlée ([Docker : gel par digest](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions)).

**Fait :** `.dockerignore` retire les chemins avant leur envoi au constructeur ; une variante propre à un Dockerfile peut prendre priorité. **Proposition :** exclure `evidence` entier, dont l’archive upstream Git LFS, `var`, `.git`, tous les `node_modules`, captures, sauvegardes, profils, secrets et `.env` ; autoriser seulement l’exemple sans secret. Copier explicitement sources utiles puis artefacts compilés et notices réelles frontend/serveur, dont les sources Twenty retenues dans `packages/ui/vendor` ([contexte Docker](https://docs.docker.com/build/concepts/context/#dockerignore-files), [exigence locale](../AGENTS.md)).

**Fait :** checkout propose `lfs:false` ; `GIT_LFS_SKIP_SMUDGE=1` conserve les pointeurs au checkout. **Proposition :** imposer les deux en CI, sans `git lfs pull`, et prouver que le build fonctionne sans l’archive Twenty complète ([actions/checkout](https://github.com/actions/checkout#usage), [Git LFS](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-config.adoc#environment-variables)).

## Démarrage, réseau et secrets

**Proposition :** Compose contient PostgreSQL 17, application et reverse proxy local ; volumes séparés base/GED, configuration et profils/secrets hors dépôt. Préflight non destructif : versions/outils/daemon, ports, origine HTTPS, chemins canoniques sans lien, espace, droits effectifs et distinction installation neuve/existante ; aucun effacement pour « réparer » un échec.

**Fait :** un port publié sans adresse vise toutes les interfaces. **Proposition :** aucun port PostgreSQL publié ; application accessible seulement au proxy ; proxy lié à l’adresse LAN choisie, avec contrôle depuis un autre poste. Ne pas assimiler réseau Docker et pare-feu du cabinet ([publication Docker](https://docs.docker.com/engine/network/port-publishing/#setting-the-default-bind-address-for-containers)).

**Fait :** Compose attend l’état running, sauf dépendance `service_healthy`/`service_completed_successfully` ; `pg_isready` peut réussir sans identifiants corrects. **Proposition :** santé PostgreSQL + migration terminée ; readiness applicative = connexion authentifiée, schéma compatible, GED accessible et maintenance inactive. Toute dépendance perdue remet l’application indisponible avec reprise bornée ([ordre Compose](https://docs.docker.com/compose/how-tos/startup-order/), [pg_isready 17](https://www.postgresql.org/docs/17/app-pg-isready.html#APP-PG-ISREADY-NOTES)).

**Fait :** `unless-stopped` redémarre avec le daemon sauf arrêt volontaire ; `depends_on.restart:true` concerne les opérations Compose explicites. **Proposition :** politique de redémarrage et reconnexion applicative, démarrage Docker de l’hôte documenté ; tester arrêt/crash/recréation, puis vrai reboot en cabinet ([redémarrage Docker](https://docs.docker.com/engine/containers/start-containers-automatically/), [dépendances](https://docs.docker.com/reference/compose-file/services/#depends_on)).

**Fait :** les secrets Compose sont des fichiers bind-mountés par service ; ils n’apportent pas un chiffrement de l’hôte. `uid/gid/mode` ne sont pas appliqués aux sources `file`. **Proposition :** répertoire hôte privé, fichiers réguliers protégés et lisibles seulement par l’UID effectif requis ; vérifier depuis le conteneur, sans compter sur le YAML pour corriger les droits ([Docker secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [spécification](https://compose-spec.github.io/compose-spec/container_spec.html#secrets)).

**Fait :** l’image PostgreSQL accepte `POSTGRES_PASSWORD_FILE` ; ses variables d’initialisation agissent seulement sur un répertoire de données vide. **Proposition :** secret initial choisi/généré sans valeur universelle ; rotation explicite en SQL et fichier coordonnés, pas simple édition de `.env` ([image officielle PostgreSQL](https://hub.docker.com/_/postgres#docker-secrets)).

**Fait :** libpq déconseille `PGPASSWORD` et accepte `PGPASSFILE`, qui doit refuser les droits groupe/autres sous Unix. **Proposition :** clients de sauvegarde avec fichier privé `0600`, paramètres non secrets séparés ; application capable de lire un fichier secret. Aucun mot de passe dans arguments, image, `set -x`, diagnostic ou export de configuration ([variables libpq](https://www.postgresql.org/docs/17/libpq-envars.html), [fichier de mots de passe](https://www.postgresql.org/docs/17/libpq-pgpass.html)).

**Fait :** Caddy peut terminer HTTPS pour un nom local avec sa CA, mais chaque poste doit lui faire confiance ; son proxy traite `X-Forwarded-*` contre l’usurpation par défaut. **Proposition :** accepter le proxy/certificat déjà administré par le cabinet ou qualifier Caddy local ; origine unique et confiance proxy restreinte. Certificat, clé et état CA persistants/protégés ; valider chaîne et cookies sur Windows. Aucun domaine ni service externe choisi ici ([HTTPS local](https://caddyserver.com/docs/automatic-https#local-https), [reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults)).

## Sauvegarde cohérente proposée

**Fait :** `pg_dump` crée un snapshot cohérent de la base au début du dump, malgré les écritures concurrentes ; `--snapshot` synchronise des sessions PostgreSQL. **Inférence :** cela ne synchronise pas la GED sur disque. L’immutabilité seule ne protège pas contre suppression/GC, fichier absent ou publication DB avant fichier ([dump SQL 17](https://www.postgresql.org/docs/17/backup-dump.html), [snapshot pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html#APP-PGDUMP-OPTIONS)).

1. **Proposition :** verrou d’exploitation exclusif commun aux sauvegardes/migrations/restaurations ; activer maintenance durable, refuser nouvelles écritures et acquisitions de jobs, drainer commandes/uploads/jobs en cours et suspendre GC. Un job non terminé dans le délai fait échouer la sauvegarde, jamais une capture déclarée cohérente.
2. **Proposition :** garder PostgreSQL actif ; une fois tous les producteurs arrêtés, exécuter `pg_dump --format=custom`, copier les objets GED réguliers immuables et la configuration stabilisée dans un staging privé. Écriture GED : publication durable du fichier avant référence DB ; fichiers temporaires/orphelins exclus. Ne pas archiver à chaud le volume `PGDATA` comme substitut du dump ([sauvegarde physique PostgreSQL](https://www.postgresql.org/docs/17/backup-file.html)).
3. **Proposition :** manifeste versionné : identifiant de sauvegarde, application/schéma, serveur/client PostgreSQL, images/architecture, date UTC, inventaire exhaustif chemins relatifs/tailles/SHA-256 et résultat de capture. Aucun secret dans le manifeste ; profils fermés et secrets dans une archive chiffrée distincte liée au même identifiant, avec procédure de récupération de clé conservée séparément par le cabinet.
4. **Proposition :** calculer les empreintes sur le staging figé, vérifier présence de chaque pièce référencée, finaliser par renommage après succès ; tout échec laisse une sauvegarde incomplète non sélectionnable et un état de maintenance récupérable. Reprendre les travaux après levée contrôlée. Chiffrer/protéger les données et copies selon l’infrastructure ; rotation seulement après restauration vérifiée, avec au moins une génération antérieure conservée.

**Fait :** `pg_dump` n’inclut pas rôles/tablespaces ; un client ancien refuse un serveur d’une majeure plus récente, et le retour vers une majeure antérieure n’est pas garanti. **Proposition :** outils et cible de restauration PostgreSQL 17 figés ; recréer explicitement les rôles locaux requis ou exporter les globals protégés. `pg_dumpall --globals-only --no-role-passwords` évite les mots de passe de rôles mais impose leur rétablissement séparé ([pg_dump 17](https://www.postgresql.org/docs/17/app-pgdump.html#APP-PGDUMP-NOTES), [pg_dumpall 17](https://www.postgresql.org/docs/17/app-pg-dumpall.html)).

## Restauration et mise à jour proposées

**Fait :** GNU tar recommande une extraction dans un répertoire vide inaccessible aux tiers ; liens et chemins absolus/`..` créent des risques. **Proposition :** valider structurellement les noms effectifs, types, nombre et tailles avant écriture ; autoriser seulement manifeste/dump/configuration et objets GED attendus. Refuser chemins absolus/parents, liens symboliques/durs, périphériques, doublons et entrées absentes/en trop ; ne pas se limiter à un grep du listing ([sécurité GNU tar](https://www.gnu.org/software/tar/manual/html_section/Security.html)).

**Proposition :** extraire sans privilège dans un staging privé neuf, sans `-P`, avec propriétaire/permissions imposés par l’outil de restauration ; n’honorer aucun propriétaire, mode spécial ou lien de l’archive. Vérifier ensuite types, chemins canoniques, tailles et empreintes sans suivre de liens, avant toute connexion de restauration. Le contrôle d’empreinte détecte une altération accidentelle, pas l’authenticité d’une archive fournie par un tiers.

**Proposition :** préflight avant toute mutation : archive complète et compatible, clés récupérables, cible explicitement identifiée, base absente ou identique à une base neuve issue de `template0`, GED/config/profils vides ; un seul objet utilisateur ou fichier existant = refus, sans nettoyage automatique. Pour remplacer une installation, restauration dans de nouveaux volumes/base puis bascule explicite et vérifiée ; ne pas ajouter `--clean` comme contournement.

**Fait :** `pg_restore --single-transaction` garantit tout ou rien et implique l’arrêt sur erreur ; `--no-owner` change la propriété des objets. Un dump peut exécuter du code choisi par le superutilisateur source. **Proposition :** créer la base de staging depuis `template0`, restaurer avec rôle local prévu, `--single-transaction --exit-on-error`, sans `--clean`, sans `--jobs` ; ne restaurer que les sauvegardes de provenance approuvée ([pg_restore 17](https://www.postgresql.org/docs/17/app-pgrestore.html), [création cible](https://www.postgresql.org/docs/17/backup-dump.html#BACKUP-DUMP-RESTORE), [avertissement pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)).

**Proposition :** comparer comptes/relations, pièces référencées et leurs empreintes, configuration et téléchargement autorisé ; exécuter `ANALYZE`, puis seulement ouvrir le trafic/jobs. Une transaction SQL ne rend pas atomique la bascule DB+répertoires : conserver maintenance et pointeur d’installation cohérent jusqu’à validation ; un échec garde la cible neuve isolée ([statistiques après restauration](https://www.postgresql.org/docs/17/backup-dump.html#BACKUP-DUMP-RESTORE)).

**Fait :** les advisory locks ont un sens applicatif et PostgreSQL n’impose pas leur emploi. **Proposition :** une connexion dédiée garde le verrou pendant migration et maintenance ; toutes les entrées l’honorent. Chaque migration transactionnelle vérifie version/checksum, valide son résultat et marque sa version dans la même transaction ; toute opération non transactionnelle doit avoir sa procédure de reprise qualifiée ([verrous PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)).

**Proposition :** mise à jour = préflight de compatibilité → maintenance/drainage → sauvegarde restaurée avec succès dans une cible isolée → migration unique → contrôles → reprise. Conserver ancienne image/configuration et sauvegarde ; en cas d’échec, restaurer l’ensemble pré-migration dans une cible neuve. Un retour d’image seul ne vaut rollback de schéma ; après réouverture, un retour à la sauvegarde perdrait les nouvelles écritures et exige une décision explicite.

## Scénarios CI Linux à rendre obligatoires

- **Paquet :** checkout sans smudge/LFS ; construire sans `evidence` ; injecter sentinelles fictives dans chemins exclus, vérifier leur absence du contexte réellement accessible et des couches/runtime ; vérifier notices frontend/serveur effectivement lisibles dans l’image finale et version Node exécutée ≥22.22.0.
- **Installation :** `compose config --quiet` puis volumes neufs ; bootstrap sans mot de passe universel, HTTP/UI via proxy, DB non publiée ; refus port occupé, droits insuffisants, secret absent et volume non vide ; persistance après recréation, arrêt volontaire et crash. Un JSON de configuration rendu ne doit jamais devenir artefact CI.
- **Sauvegarde :** records liés + pièces fictives + job actif ; tenter écriture/GC pendant maintenance, provoquer timeout/panne du dump puis reprendre ; sauvegarde nominale → restauration dans cible neuve ; comparer valeurs attendues indépendantes, relations, octets, configuration et droits d’accès, pas seulement le code de sortie ou `pg_restore --list`.
- **Refus sans dégâts :** base déjà peuplée, GED avec sentinelle, fichier manquant, empreinte incorrecte, mauvaise clé/version, archive tronquée, `../`, absolu, lien symbolique/dur, doublon, mode setuid, dépassement ; contrôler les sentinelles hors staging et l’installation d’origine après chaque refus.
- **Mise à jour/reprise :** fixture d’ancien schéma, deux démarrages de migration concurrents, interruption à chaque frontière DB/fichiers, migration volontairement invalide, DB indisponible puis revenue ; vérifier une seule migration, aucun état partiel exposé, jobs rejouables sans doublon, retour au backup et readiness exacte.
- **Diagnostic :** sortie limitée à états, versions, espace, résultat des contrôles et codes d’erreur ; injecter des secrets fictifs reconnaissables et prouver leur absence des journaux/artefacts, y compris URL PostgreSQL, cookies, en-têtes, profils et erreurs de sous-processus. Conserver uniquement diagnostics filtrés avec rétention courte.

**Preuves présentes :** contrats locaux lus, sources officielles consultées, index OCI Docker interrogés via API HTTPS avec vérification TLS et digests des manifestes Linux lus dans leurs entrées. **Preuves absentes :** aucun build/pull/conteneur, test applicatif, sauvegarde/restauration ou CI exécuté dans cette recherche ; Docker n’a pas de daemon local disponible selon l’état transmis. Le PostgreSQL 17 isolé local reste utilisable pour de futurs essais, sans valider le paquet. Reboot réel, certificats/confiance Windows, stockage, chiffrement/récupération de clé, copie/rotation et charge restent à qualifier ; vrais comptes et administrations en toute dernière phase. Aucun service cloud, domaine, compte ou daemon installé ; aucun paquet, code applicatif ou commit modifié.
